## Latency

Scheduler, interrupt and multimedia-class settings that affect how quickly your input reaches the game and how quickly the frame reaches your monitor.

### MMCSS: release reserved background CPU

` lat.mmcss.system-responsiveness `

**Tier:** core &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** medium &nbsp;·&nbsp; **Windows:** 10, 11

The Multimedia Class Scheduler reserves a percentage of CPU for background tasks whenever a multimedia-class thread is running. The default of 20 means one fifth of scheduling capacity is held back from the game. Setting it to 0 hands that capacity to the foreground title. On a 6-core part like the 11400F, where Fortnite can genuinely saturate the CPU during a busy endgame, this is worth having.

<details><summary>What it changes</summary>

```
registry  HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Multimedia\SystemProfile\SystemResponsiveness = 0
```

</details>

### Disable network throttling for multimedia apps

` lat.mmcss.network-throttling `

**Tier:** core &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** medium &nbsp;·&nbsp; **Requires restart** &nbsp;·&nbsp; **Windows:** 10, 11

Windows throttles non-multimedia network traffic to roughly 10 packets per millisecond while a multimedia-class application is running. Fortnite's gameplay traffic is small, frequent UDP datagrams — exactly the shape this throttle interferes with. Setting the index to 0xFFFFFFFF disables the throttle entirely. This is one of the few genuinely network-related registry tweaks with a real mechanism behind it.

<details><summary>What it changes</summary>

```
registry  HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Multimedia\SystemProfile\NetworkThrottlingIndex = 4294967295
```

</details>

### MMCSS: raise the Games task priority class

` lat.mmcss.games-task `

**Tier:** core &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** medium &nbsp;·&nbsp; **Windows:** 10, 11

Fortnite registers itself with the MMCSS 'Games' task. That task's profile controls the GPU priority, thread priority and scheduling category the OS grants the game's render and input threads. The stock profile is conservative. Raising GPU Priority to 8, thread Priority to 6 and both scheduling categories to High gives the render thread better odds of being serviced promptly, which shows up as steadier frame pacing rather than raw FPS.

<details><summary>What it changes</summary>

```
registry  HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Multimedia\SystemProfile\Tasks\Games\GPU Priority = 8
registry  HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Multimedia\SystemProfile\Tasks\Games\Priority = 6
registry  HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Multimedia\SystemProfile\Tasks\Games\Scheduling Category = High
registry  HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Multimedia\SystemProfile\Tasks\Games\SFIO Priority = High
```

</details>

### Favour the foreground application in the scheduler

` lat.scheduler.priority-separation `

**Tier:** core &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** medium &nbsp;·&nbsp; **Windows:** 10, 11

Win32PrioritySeparation controls quantum length and how strongly the foreground process is boosted. The value 38 (0x26) means short, variable quanta with a 3:1 foreground bias — the game gets more, shorter turns on the CPU, which reduces the worst-case wait before its input and render threads run. Short quanta specifically help worst-case latency rather than average throughput, which is the trade you want in a shooter.

<details><summary>What it changes</summary>

```
registry  HKLM:\SYSTEM\CurrentControlSet\Control\PriorityControl\Win32PrioritySeparation = 38
```

</details>

### Disable CPU power throttling

` lat.power.throttling-off `

**Tier:** core &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** high &nbsp;·&nbsp; **Windows:** 10, 11

Windows power throttling parks threads onto low-power states when it believes a workload is not latency-sensitive. Its heuristics regularly misjudge game threads, producing brief clock dips that appear as inconsistent frametimes and momentary input sluggishness. On a desktop with no battery to preserve, there is no reason to leave it on.

<details><summary>What it changes</summary>

```
registry  HKLM:\SYSTEM\CurrentControlSet\Control\Power\PowerThrottling\PowerThrottlingOff = 1
```

</details>

### Disable dynamic timer tick

` lat.boot.disable-dynamic-tick `

**Tier:** core &nbsp;·&nbsp; **Risk:** medium &nbsp;·&nbsp; **Impact:** medium &nbsp;·&nbsp; **Requires restart** &nbsp;·&nbsp; **Windows:** 10, 11

Dynamic tick lets the kernel suspend the periodic timer interrupt when idle to save power. A number of systems handle the resume from that suspension badly, producing DPC latency spikes that land as micro-stutter. Disabling it keeps the tick running continuously. The cost is power draw, which is irrelevant on a desktop. Verify with the DPC latency check afterwards — this is a tweak whose benefit is genuinely machine-dependent, so measure rather than assume.

<details><summary>What it changes</summary>

```
bcdedit   disabledynamictick = yes
```

</details>

### Stop forcing the HPET platform clock

` lat.boot.unforce-hpet `

**Tier:** core &nbsp;·&nbsp; **Risk:** medium &nbsp;·&nbsp; **Impact:** medium &nbsp;·&nbsp; **Requires restart** &nbsp;·&nbsp; **Windows:** 10, 11

Old guides tell people to run 'bcdedit /set useplatformclock yes'. On modern hardware this is actively harmful: it forces Windows onto the High Precision Event Timer, whose reads are far more expensive than the invariant TSC the kernel would otherwise use, raising overhead on every timestamp the game takes. This tweak removes the forced setting so Windows selects the best available clock source itself. If you never set it, this is a harmless no-op.

<details><summary>What it changes</summary>

```
bcdedit   useplatformclock = <delete / absent>
```

</details>

### Disable Game DVR background capture

` lat.gamedvr.disable-capture `

**Tier:** core &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** high &nbsp;·&nbsp; **Windows:** 10, 11

Game DVR keeps a rolling capture buffer running behind every game so you can retroactively save a clip. That means continuous GPU-side encode work and an extra present-path hook, on a GPU that is already your bottleneck. Turning it off is one of the highest value-per-risk changes available, and it is the single most commonly cited fix for the specific symptom of good FPS with bad feel.

<details><summary>What it changes</summary>

```
registry  HKCU:\System\GameConfigStore\GameDVR_FSEBehaviorMode = 2
registry  HKLM:\SOFTWARE\Policies\Microsoft\Windows\GameDVR\AllowGameDVR = 0
registry  HKCU:\Software\Microsoft\Windows\CurrentVersion\GameDVR\AppCaptureEnabled = 0
registry  HKCU:\Software\Microsoft\Windows\CurrentVersion\GameDVR\HistoricalCaptureEnabled = 0
```

</details>

### Enable Windows Game Mode

` lat.gamemode.enable `

**Tier:** core &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** medium &nbsp;·&nbsp; **Windows:** 10, 11

Game Mode had a poor reputation from its early Windows 10 implementation and a lot of guides still tell you to disable it. On current Windows 11 it suppresses background work such as driver installs and update scans while a game is in the foreground, and it is a prerequisite for some of the OS-side scheduling behaviour the game relies on. Leaving it on is the correct choice now, and this tweak exists specifically to undo the bad old advice.

<details><summary>What it changes</summary>

```

registry  HKCU:\Software\Microsoft\GameBar\AutoGameModeEnabled = 1
```

</details>

### Reduce desktop compositor overhead

` lat.dwm.reduce-compositor-work `

**Tier:** aggressive &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** low &nbsp;·&nbsp; **Windows:** 10, 11

Animations, transparency and shadow effects give the Desktop Window Manager continuous work to do on the same GPU the game is saturating. In true exclusive fullscreen the compositor is largely bypassed and this matters little, but it helps in borderless windowed and it removes a source of alt-tab stutter. Honest expectation: small, and mostly felt on the desktop rather than in a match.

### Disable Nagle's algorithm (TCP only)

` lat.nagle.disable-tcp-coalescing `

**Tier:** aggressive &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** low &nbsp;·&nbsp; **Requires restart** &nbsp;·&nbsp; **Windows:** 10, 11

Read this one before enabling it. Nagle's algorithm coalesces small TCP writes to reduce packet overhead, adding up to ~200ms of delay to small sends. Every Fortnite guide on the internet tells you to disable it. However, Fortnite's actual gameplay traffic is UDP, which Nagle does not touch at all — so this will not improve your in-game feel. It affects TCP traffic such as launcher and matchmaking calls. It is included because it is harmless and mildly helpful for those, and because you should know it is not the input-delay fix it is usually sold as. The real fix for your input delay is the frame cap.

<details><summary>What it changes</summary>

```
registry  HKLM:\SOFTWARE\Microsoft\MSMQ\Parameters\TCPNoDelay = 1
```

</details>


## Power

Power policy. On a desktop these settings cost you nothing but electricity and heat, and several of them directly affect controller responsiveness.

### Disable USB selective suspend

` pwr.usb.selective-suspend-off `

**Tier:** core &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** critical &nbsp;·&nbsp; **Windows:** 10, 11

This is the most important power setting on the list for a controller player. USB selective suspend lets Windows put an idle USB device into a low-power state; waking it costs milliseconds and the wake is triggered by the very input you are trying to send. On a wired controller this produces the exact symptom of the first input after a pause feeling mushy or dropped, while inputs during continuous movement feel fine. Disabling it keeps the controller's USB endpoint hot at all times.

<details><summary>What it changes</summary>

```
power     usb-selective-suspend = 0
```

</details>

### Hold minimum processor state at 100%

` pwr.cpu.min-state-100 `

**Tier:** core &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** high &nbsp;·&nbsp; **Windows:** 10, 11

Frequency ramping is not instant. When the CPU is sitting at a low multiplier and a frame suddenly needs work, the clock has to climb, and the first frames after that transition arrive late. Pinning the minimum state to 100% removes the ramp entirely so the clock is already where it needs to be. The honest cost is higher idle temperature, more fan noise and more power draw — all irrelevant on a desktop you use for one game. If your cooling is marginal, watch temperatures after applying this.

<details><summary>What it changes</summary>

```
power     processor-min-state = 100
power     processor-max-state = 100
```

</details>

### Disable CPU core parking

` pwr.cpu.no-core-parking `

**Tier:** core &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** high &nbsp;·&nbsp; **Windows:** 10, 11

Core parking takes idle cores offline to save power and unparks them on demand. Unparking is not free and the heuristic reacts to load rather than predicting it, so a sudden burst of work — a squad pushing you, a big build fight — lands on a subset of cores while the rest wake up. On a 6-core chip that is a meaningful fraction of your CPU arriving late. Forcing 100% of cores to stay unparked removes the transition.

<details><summary>What it changes</summary>

```
power     core-parking-min-cores = 100
```

</details>

### Set processor boost mode to aggressive

` pwr.cpu.boost-aggressive `

**Tier:** core &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** medium &nbsp;·&nbsp; **Windows:** 10, 11

Boost mode governs how eagerly Windows requests turbo frequencies. Aggressive mode (value 2) asks for turbo as soon as demand appears rather than waiting for sustained load. Fortnite's CPU demand is spiky by nature — quiet while looting, sharp during fights — which is precisely the pattern a conservative boost policy handles worst.

<details><summary>What it changes</summary>

```
power     processor-boost-mode = 2
```

</details>

### Disable PCI Express link power management

` pwr.pcie.aspm-off `

**Tier:** core &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** medium &nbsp;·&nbsp; **Windows:** 10, 11

Active State Power Management lets PCIe links drop into low-power states between transfers. Both your GPU and your network adapter sit on PCIe. Link state transitions add latency to the first transfer after an idle period, which affects GPU command submission and, more importantly for you, network packet delivery. Turning ASPM off keeps every link at full power.

<details><summary>What it changes</summary>

```
power     pcie-aspm = 0
```

</details>

### Never spin down storage

` pwr.disk.never-sleep `

**Tier:** core &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** low &nbsp;·&nbsp; **Windows:** 10, 11

A drive that has been powered down has to come back before it can serve the next texture or asset stream, producing a hitch. Fortnite streams assets continuously during a match. Setting the idle timeout to never removes the possibility. Minor on an SSD, more noticeable on a mechanical drive.

<details><summary>What it changes</summary>

```
power     disk-idle-timeout = 0
```

</details>

### Disable sleep and hibernate on AC

` pwr.sleep.disable `

**Tier:** aggressive &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** low &nbsp;·&nbsp; **Windows:** 10, 11

Sleep transitions are a recurring cause of USB devices re-enumerating incorrectly on wake — the classic 'my controller stopped working until I unplugged it' problem. On a machine that exists to run one game, there is no reason to allow the transition at all.

<details><summary>What it changes</summary>

```
power     sleep-after = 0
power     hibernate-after = 0
```

</details>


## Windows 11

Windows 11 specific overhead. The virtualisation-based security items here are the largest single CPU win available to you in software.

### Disable Virtualisation Based Security (VBS)

` w11.vbs.disable `

**Tier:** aggressive &nbsp;·&nbsp; **Risk:** high &nbsp;·&nbsp; **Impact:** critical &nbsp;·&nbsp; **Requires restart** &nbsp;·&nbsp; **Windows:** 11

VBS runs Windows itself inside a hypervisor so that security boundaries can be enforced by the hypervisor rather than the kernel. That isolation is not free: it adds overhead to memory access and to every transition the kernel makes, and independent testing has repeatedly measured a meaningful CPU cost in games, often in the mid single digits to low teens in percentage terms. On a 6-core i5-11400F that is the difference between holding a frametime target in an endgame and not. READ THE TRADE-OFF: this genuinely reduces your protection against kernel-level exploits and malicious drivers. You are choosing frames over a security layer. That is a legitimate choice on a machine that only runs one game, but it is a real choice, not a free win.

<details><summary>What it changes</summary>

```
registry  HKLM:\SYSTEM\CurrentControlSet\Control\DeviceGuard\EnableVirtualizationBasedSecurity = 0
registry  HKLM:\SYSTEM\CurrentControlSet\Control\DeviceGuard\RequirePlatformSecurityFeatures = 0
```

</details>

### Disable Memory Integrity (HVCI / Core Isolation)

` w11.hvci.disable `

**Tier:** aggressive &nbsp;·&nbsp; **Risk:** high &nbsp;·&nbsp; **Impact:** critical &nbsp;·&nbsp; **Requires restart** &nbsp;·&nbsp; **Windows:** 11

Hypervisor-Enforced Code Integrity validates every driver through the hypervisor before it is allowed to run. It is the component of Core Isolation with the highest measured performance cost, and it is the one most often responsible for the gap between benchmark numbers and what a Windows 11 machine actually delivers. Disabling it recovers that cost. Same trade-off statement as VBS applies: this is a real reduction in kernel-level protection. Windows Security will show a warning banner after this, which is expected and accurate rather than a bug.

<details><summary>What it changes</summary>

```
registry  HKLM:\SYSTEM\CurrentControlSet\Control\DeviceGuard\Scenarios\HypervisorEnforcedCodeIntegrity\Enabled = 0
```

</details>

### Stop launching the hypervisor at boot

` w11.hypervisor.launchtype-off `

**Tier:** nuclear &nbsp;·&nbsp; **Risk:** high &nbsp;·&nbsp; **Impact:** high &nbsp;·&nbsp; **Requires restart** &nbsp;·&nbsp; **Windows:** 11

Even with VBS and HVCI switched off, the hypervisor can still be loaded at boot, and while it is loaded Windows continues to run as a guest with the associated transition overhead. Setting the launch type to off ensures the machine runs on bare metal. This disables Hyper-V, Windows Sandbox, WSL2 and Windows Subsystem for Android — none of which you use, but revert this tweak if you ever want them back. Easy Anti-Cheat does not require the hypervisor and is unaffected.

<details><summary>What it changes</summary>

```
bcdedit   hypervisorlaunchtype = off
```

</details>

## Network

Network adapter and stack settings. Read the honesty note: most 'gaming network tweaks' circulating online do nothing. These are the ones with an actual mechanism.

> **honesty note**: Your ping is dominated by the physical distance between you and the Epic datacentre plus your ISP's routing. Nothing in this file changes either. What these tweaks address is jitter and the small, local delays added between your NIC receiving a packet and the game seeing it. If you are 35ms from the server, you will still be roughly 35ms from the server after applying every tweak here — but the variance around that number should tighten, and tighter variance is what actually feels better in a build fight.

### Disable Energy Efficient Ethernet

` net.nic.disable-eee `

**Tier:** core &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** high &nbsp;·&nbsp; **Windows:** 10, 11

Energy Efficient Ethernet (802.3az) lets the link enter a low-power idle state between frames and wake when traffic resumes. The wake transition costs real microseconds to low milliseconds, and game traffic is exactly the bursty, small-packet pattern that keeps triggering it. This is one of the few adapter settings that produces a measurable jitter improvement rather than a placebo one. Several keyword variants are attempted because vendors name it differently; the ones your NIC does not expose are skipped silently.

<details><summary>What it changes</summary>

```
nic       *EEE = 0
nic       EnableGreenEthernet = 0
nic       AdvancedEEE = 0
nic       EEELinkAdvertisement = 0
```

</details>

### Disable NIC interrupt moderation

` net.nic.disable-interrupt-moderation `

**Tier:** core &nbsp;·&nbsp; **Risk:** medium &nbsp;·&nbsp; **Impact:** high &nbsp;·&nbsp; **Windows:** 10, 11

Interrupt moderation batches incoming packets and raises one interrupt for the group instead of one per packet. That is excellent for throughput and bad for latency: your position update can sit in the NIC waiting for the batch to fill or the timer to expire. Disabling it means every packet interrupts immediately. The honest cost is measurably higher CPU usage from the extra interrupts — on a 6-core chip this is a real trade, so if you see CPU-bound frametime regressions after this, revert it. For most players the latency win is worth it.

<details><summary>What it changes</summary>

```
nic       *InterruptModeration = 0
nic       ITR = 0
```

</details>

### Stop the NIC from entering power-saving states

` net.nic.disable-power-saving `

**Tier:** core &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** medium &nbsp;·&nbsp; **Windows:** 10, 11

Separate from EEE, most adapters expose their own power-saving and selective-suspend behaviour. The same reasoning applies: a link that has powered down has to come back before it can deliver the packet carrying your opponent's position. On a desktop there is no reason for the network card to ever save power.

```

nic       *SelectiveSuspend = 0
nic       ULPMode = 0
nic       *ModernStandbyWoLMagicPacket = 0
```

</details>

### Enable Receive Side Scaling

` net.nic.enable-rss `

**Tier:** core &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** medium &nbsp;·&nbsp; **Windows:** 10, 11

Without RSS, all received network processing is pinned to CPU core 0. Core 0 is also where a great deal of other system work lands, so network processing ends up queued behind unrelated work at exactly the wrong moments. RSS spreads receive processing across cores. This is a case where the default is sometimes already correct — the tweak is idempotent and will report as already-applied if so.

<details><summary>What it changes</summary>

```
nic       *RSS = 1
```

</details>

### Disable Ethernet flow control

` net.nic.disable-flow-control `

**Tier:** aggressive &nbsp;·&nbsp; **Risk:** medium &nbsp;·&nbsp; **Impact:** low &nbsp;·&nbsp; **Windows:** 10, 11

Flow control lets a congested link tell the sender to pause. For a game, a paused link is worse than a dropped packet: the game's netcode already handles loss gracefully, but a pause delays everything behind it. Realistically this almost never triggers on a home gigabit link with a single PC, so expect no perceptible change — it is included for completeness rather than because it will fix anything.

<details><summary>What it changes</summary>

```
nic       *FlowControl = 0
```

</details>

### Stop Windows overriding TCP autotuning

` net.tcp.disable-heuristics `

**Tier:** aggressive &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** low &nbsp;·&nbsp; **Windows:** 10, 11

Windows scaling heuristics can silently override the configured receive window autotuning level based on its own guesses about the connection. Pinning autotuning to normal and disabling the heuristic makes behaviour predictable. This affects downloads and launcher traffic rather than UDP gameplay packets, so do not expect it to change your in-game feel.

<details><summary>What it changes</summary>

```

```

</details>

### Enable Explicit Congestion Notification

` net.tcp.enable-ecn `

**Tier:** aggressive &nbsp;·&nbsp; **Risk:** medium &nbsp;·&nbsp; **Impact:** low &nbsp;·&nbsp; **Windows:** 10, 11

ECN lets routers signal congestion by marking packets instead of dropping them. Where the path supports it end to end this reduces retransmission and smooths latency under load. Support is inconsistent and a badly behaved middlebox can make things worse, which is why this sits at aggressive rather than core. Behind a double-NAT setup specifically, test this one and revert it if your connection gets less stable rather than more.

<details><summary>What it changes</summary>

```
tcp       EcnCapability = Enabled
```

</details>

## Nuclear

Maximum-aggression tier. Every tweak in this file has a genuine downside that is not merely theoretical. They are here because you asked for the ceiling to be this high, and each one states plainly what it costs you.

> **read this first**: These are not 'more optimisation'. They are trades. Disabling Windows Update means you stop receiving security patches AND the driver and platform fixes that sometimes improve game performance. Disabling Defender means the machine is unprotected — and a machine used for downloading Fortnite configs, crosshair overlays and 'FPS boosters' from the internet is exactly the machine that gets compromised. Apply these knowing what you are buying.

### Disable Microsoft Defender real-time protection

` nuke.defender.realtime-off `

**Tier:** nuclear &nbsp;·&nbsp; **Risk:** high &nbsp;·&nbsp; **Impact:** high &nbsp;·&nbsp; **Requires restart** &nbsp;·&nbsp; **Windows:** 10, 11

Real-time protection scans every file on access. Fortnite streams thousands of asset reads during a match and each one passes through the filter driver. Disabling it removes that overhead and is a measurable win on load times and asset-streaming hitches. THIS WILL NOT WORK ON ITS OWN IF TAMPER PROTECTION IS ENABLED — Windows will silently revert these values within minutes and the tool will report the tweak as drifted. You must first turn Tamper Protection off manually in Windows Security, Virus and threat protection, Manage settings. FortressOne deliberately does not attempt to bypass Tamper Protection: anything that defeats it is indistinguishable from malware behaviour and is exactly the sort of thing that gets a tool flagged. The security cost is real and permanent until reverted.

<details><summary>What it changes</summary>

```
registry  HKLM:\SOFTWARE\Policies\Microsoft\Windows Defender\DisableAntiSpyware = 1
registry  HKLM:\SOFTWARE\Policies\Microsoft\Windows Defender\Real-Time Protection\DisableRealtimeMonitoring = 1
registry  HKLM:\SOFTWARE\Policies\Microsoft\Windows Defender\Real-Time Protection\DisableBehaviorMonitoring = 1
registry  HKLM:\SOFTWARE\Policies\Microsoft\Windows Defender\Real-Time Protection\DisableOnAccessProtection = 1
registry  HKLM:\SOFTWARE\Policies\Microsoft\Windows Defender\Real-Time Protection\DisableScanOnRealtimeEnable = 1
```

</details>

### Exclude Fortnite from Defender scanning (safer alternative)

` nuke.defender.exclude-fortnite `

**Tier:** aggressive &nbsp;·&nbsp; **Risk:** medium &nbsp;·&nbsp; **Impact:** high &nbsp;·&nbsp; **Windows:** 10, 11

This is the tweak you should almost certainly apply INSTEAD of disabling Defender entirely. It excludes the Fortnite and Epic install directories from real-time scanning, which captures nearly all of the performance benefit — because the game's asset reads are what the scanner was slowing down — while leaving the rest of the machine protected. The paths are resolved at apply time by the Fortnite module. Chosen over the full disable, this is the better engineering trade by a wide margin.

<details><summary>What it changes</summary>

```
registry  HKLM:\SOFTWARE\Policies\Microsoft\Windows Defender\PUAProtection = 0
```

</details>

### Disable Windows Update entirely

` nuke.windowsupdate.disable `

**Tier:** nuclear &nbsp;·&nbsp; **Risk:** high &nbsp;·&nbsp; **Impact:** medium &nbsp;·&nbsp; **Requires restart** &nbsp;·&nbsp; **Windows:** 10, 11

Windows Update downloads and installs in the background and periodically demands a restart, sometimes mid-session. Disabling it removes that class of interruption completely. The costs are serious and worth stating plainly: you stop receiving security patches, you stop receiving the platform and scheduler fixes that have historically improved game performance on Windows 11, and eventually your build reaches end of support. A better pattern for most people is to leave this enabled and instead set active hours plus a metered connection so updates never install while you play. Apply this only if you intend to manually update every few months.

<details><summary>What it changes</summary>

```
service   wuauserv -> Disabled
service   UsoSvc -> Disabled
service   WaaSMedicSvc -> Disabled
registry  HKLM:\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate\AU\NoAutoUpdate = 1
```

</details>

### Disable hibernation and remove hiberfil.sys

**Tier:** aggressive &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** low &nbsp;·&nbsp; **Requires restart** &nbsp;·&nbsp; **Windows:** 10, 11

Hibernation reserves a file equal to a large fraction of your RAM on the system drive — several gigabytes on a 16GB machine. Disabling it reclaims that space and removes hybrid sleep, which is a common source of USB devices misbehaving after a resume. Note this also disables Fast Startup, which is a good thing here: Fast Startup means the machine never fully cold boots, so driver state and tweaks that apply at boot can persist in stale form and produce confusing results.

### Disable Fast Startup

` nuke.fastboot.disable `

**Tier:** core &nbsp;·&nbsp; **Risk:** low &nbsp;·&nbsp; **Impact:** medium &nbsp;·&nbsp; **Requires restart** &nbsp;·&nbsp; **Windows:** 10, 11

Fast Startup means 'shut down' actually hibernates the kernel session rather than powering off. The practical consequence for you is that driver state, USB enumeration and boot-time tweaks carry over between sessions instead of being reinitialised. That is the single most common reason a tweak appears not to work, or a controller that misbehaved keeps misbehaving after a restart. Turning it off costs a few seconds of boot time and makes the machine's behaviour reproducible, which matters enormously when you are trying to test whether a change helped.

<details><summary>What it changes</summary>

```
registry  HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager\Power\HiberbootEnabled = 0
```

</details>
